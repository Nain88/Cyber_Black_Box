# Cloud Box + Windows Docker + Kali attack-simulation lab

**Drop-in add-on for `Nain88/cloud-box` at commit `96d78bc` (November 5, 2026).**
It leaves the existing Cloud Box backend, case dashboard, database and collector code unchanged. Copy **all files and directories** from this ZIP into the *root* of the `cloud-box` repository. Existing files remain untouched, including the original `README.md` (this add-on uses `LAB-SETUP.md`).

**What you get:** a separate web dashboard in Docker Desktop on Windows, three limited attack-like scenarios targeting an instrumented Kali VM, a Kali-side observation service, and a Windows relay that sends genuine target-side observations to your existing Cloud Box API as clearly labelled `lab.fixture` evidence. Cloud Box seals the events and creates basic severity-based alerts. **No real exploitation, shell commands, denial of service or unapproved targets.**

## Requirements

- Windows 10/11 with Docker Desktop running (Linux containers enabled).
- Your existing Cloud Box project running natively on Windows at **http://127.0.0.1:8765** using `Start-Cyber-Black-Box.cmd`, with a working administrator account. Leave Cloud Box running.
- Kali Linux VM in VMware/VirtualBox, preferably host-only or private NAT, with Python 3.10+.
- Windows and the Docker container must both reach Kali's private IPv4 address on TCP ports **8088, 8089 and 8090**. Ensure Windows Firewall and Kali firewall permit only this private test traffic.
- Python 3.12 or newer on Windows (the Cloud Box `.venv` can be reused by the relay).
- Windows and Kali clocks must be reasonably synchronized (within 60 seconds).

## Quick start (the existing Windows-native Cloud Box)

### 1. Start Cloud Box on Windows

From the root of the original project, double-click `Start-Cyber-Black-Box.cmd`, and log in at <http://127.0.0.1:8765>. Cloud Box must be running with background workers enabled. Do not change Cloud Box's listening address to `0.0.0.0`.

### 2. Find Kali's private IP and copy the lab files

In the Kali VM, open a terminal:

```bash
ip -brief address
python3 --version
```

Identify the private address for the VM interface reachable from Windows, e.g. `192.168.56.101` (your address will differ). Copy this ZIP's project files into the Kali project as well, or use GitHub after you upload the new files. Only `lab/kali/` is needed at runtime on Kali.

### 3. Set a private Kali shared key

Choose one 32+ character random secret for **only the Kali target and Windows relay**. This is different from the dashboard operator password and Cloud Box login credentials. On Kali:

```bash
cd /path/to/cloud-box/lab/kali
./start-kali.sh
```

The script securely prompts for your chosen `LAB_SHARED_KEY`, so it is not entered directly into shell history. The decoy now listens at `http://KALI_PRIVATE_IP:8088` and TCP ports 8089/8090. The terminal prints its local SQLite evidence path. **Use a test-only private VM and do not expose this service to the public Internet.**

From Windows PowerShell, verify reachability:

```powershell
Test-NetConnection 192.168.56.101 -Port 8088
Invoke-RestMethod http://192.168.56.101:8088/health
```

Replace the example IP with the **actual Kali IP**. If connectivity fails, check VMware/VirtualBox network mode and Kali firewall before continuing. After starting Docker you can run `.\lab\windows\Test-Lab-Connectivity.ps1` to test Windows-to-Kali, Docker-to-Kali and Windows-to-Cloud-Box paths separately.

### 4. Start the Docker attacker dashboard (Windows)

In PowerShell from the Cloud Box repository root:

```powershell
.\lab\windows\Start-Attack-Lab.ps1 -KaliIP '192.168.56.101'
```

This creates `lab/.env` with a random dashboard password, builds the Docker container, and opens <http://127.0.0.1:8844>. Save the printed password and use it to log in. Docker Desktop must be running. If PowerShell blocks scripts, use an appropriately authorized PowerShell session or invoke this one-time script with `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\lab\windows\Start-Attack-Lab.ps1 -KaliIP 192.168.56.101`.

Equivalent manual Docker command if you have already created `lab/.env`:

```powershell
docker compose --env-file lab/.env -f compose.lab.yml up -d --build
```

The dashboard is a **separate web app**; Cloud Box's main dashboard remains at port 8765.

### 5. Enroll the Windows relay in Cloud Box

In the normal Cloud Box dashboard, go to **Collectors > Enroll collector**, choose a name such as `Kali Lab Relay` and OS `Linux`, then copy its **single-use enrollment token**. The relay is a Windows process that collects observations from Kali; the OS selection is descriptive.

Run this in Windows PowerShell at the repository root:

```powershell
.\lab\windows\Start-Relay.ps1 -KaliIP '192.168.56.101'
```

On the first run, you are prompted for the enrollment token and the same `LAB_SHARED_KEY` you used in Kali. This will save collector credentials locally in `lab/.lab-state/relay.json` (Git ignored) and begin polling Kali every three seconds. **Leave the relay PowerShell window running** during the demo. No Cloud Box credentials are supplied to the Docker simulator.

### 6. Connect the collector to an administrator-owned Cloud Box case

Because Cloud Box admins cannot automatically see raw evidence outside their assigned cases, run this one-time case setup helper on Windows:

```powershell
.\lab\windows\Configure-CloudBox-Intake.ps1
```

Enter the Cloud Box administrator username and password when prompted. The script creates or reuses an admin-owned case named **Kali Attack Lab** and assigns the enrolled `Kali Lab Relay` collector's incoming observations to it. It uses authenticated Cloud Box APIs and does not store the admin password. If your Cloud Box administrator uses MFA, enter the current authenticator code when the helper asks for it.

### 7. Run the demo

1. Visit <http://127.0.0.1:8844> and sign into the lab dashboard.
2. Check that **Kali Decoy** is **Online**.
3. Click **Run scenario** on one of the three cards.
4. Watch the Windows relay terminal: `Forwarded N observed records`.
5. In <http://127.0.0.1:8765>, open **Case workspace > Kali Attack Lab**, **Live monitor** or **Alerts & anomalies**.
6. Open a record to inspect `lab.fixture`, the event's target-side timestamp, source address, original raw bytes, SHA-256 evidence integrity and `lab_simulation: true` flag.
7. Create a Cloud Box checkpoint/report as usual to demonstrate end-to-end custody and preservation.

The lab does **not** inject fictional Suricata alerts. Its evidence is genuinely recorded by Kali's HTTP/TCP decoys and then faithfully forwarded to Cloud Box under a simulation source label.

## Available attack-like scenarios

| Dashboard button | Real network action | Kali observation | Cloud Box event type |
|---|---|---|---|
| Port reconnaissance | Six TCP connections to decoy ports 8089 and 8090 | Source IP, port, timestamp | `lab.port.probe` |
| Failed sign-ins | Six invalid POST requests to `/api/login` | Username (password never stored), source IP | `lab.auth.failure` |
| Web path probing | Five harmless GET requests to nonexistent endpoints | URL path, source IP, response 404 | `lab.http.probe` |

All cases are bounded by a single hardcoded target, fixed path/port lists, small request counts, minimum delay, one concurrent scenario and a six-second cooldown. These are controlled **attack simulations**, not exploitable services or a vulnerability scanner.

## Troubleshooting

**Dashboard says Kali unreachable:** Check `KALI_IP` in `lab/.env`, Kali target terminal, and `Test-NetConnection`. Docker's own networking must also reach Kali. Run `docker compose --env-file lab/.env -f compose.lab.yml logs -f` to inspect the dashboard container.

**Kali events don't appear in Cloud Box:** Confirm the Windows relay window is running, that its token has not been revoked, and that Cloud Box is available at `127.0.0.1:8765`. Run `python lab/relay/relay.py run --once` for diagnostic output. Confirm the case intake helper completed successfully; admin access is intentionally case-scoped.

**HMAC authentication failed:** The `LAB_SHARED_KEY` must match on Kali and Windows relay. Also check the systems' clocks. No key is sent in the target event polling URL.

**Cloud Box shows STAGED but not SEALED:** Cloud Box's own worker is responsible for sealing. Look at its diagnostics/worker status and pending receipts. A slow or failed seal is not treated as successful forensic preservation.

**Your Kali target was recreated:** Its SQLite data folder contains a persistent target ID used for deduplication. Do not delete the folder during a run. If it changes, the relay intentionally refuses to silently reuse its old cursor. Preserve the old evidence, then explicitly enroll a new collector.

**MFA login to intake helper:** Cloud Box requires the current TOTP code when MFA is enabled. Enter it when prompted; the rest of the lab does not require admin credentials once case intake is linked.

## Tests

All Python components use the standard library, so no additional Python packages are needed for the lab components. The ZIP also includes a separate GitHub Actions workflow to run these tests on Windows and Ubuntu after you upload it. Run the local test suite:

```powershell
python -m unittest discover -s lab/tests -v
```

## Stop and restart

Stop the Docker UI without deleting anything:

```powershell
docker compose --env-file lab/.env -f compose.lab.yml down
```

Restart it with the same `.env`:

```powershell
docker compose --env-file lab/.env -f compose.lab.yml up -d --build
```

Stop the Windows relay with Ctrl+C, and the Kali target with Ctrl+C. Their locally persisted records, cursor and credentials remain in their respective ignored data folders.

## Integration scope and why nothing in Cloud Box core is patched

The current Cloud Box code already accepts collector events of source type `lab.fixture`, stores raw bytes, creates basic alerts for severity 3+ observations, and supports an `intake_case_id` for automatic case linking. Therefore **no modifications to `cbb/api.py`, `cbb/service.py`, `cbb/schema.py` or existing dashboard files are necessary** for this isolated lab flow.

The main limitation is intentional: this setup demonstrates logging of *actual requests received by the Kali decoy*, not full-network intrusion detection. For genuine Suricata detections, separately install and configure Suricata on an interface that can see Docker-to-Kali traffic and enroll its EVE output through the existing Cloud Box agent.

## Security notes

Use only your own authorized Kali VM. Keep it on an isolated/private network. Never commit `lab/.env`, `lab/.lab-state/`, or Kali's SQLite data to GitHub. Do not expose the dashboard, Kali decoy or the Cloud Box HTTP service publicly. See [lab/docs/ARCHITECTURE.md](lab/docs/ARCHITECTURE.md) for the trust boundaries and limitations.
